# ADR 0001：Agent 首版范围与不可变约束

- 状态：已接受
- 决策日期：2026-07-29
- 适用范围：本项目的第一个可运行版本

## 1. 背景与学习目标

本项目用于从零学习并实现一个最小但结构完整的 Agent。首版重点不是接入尽可能多的模型和工具，而是建立一条可理解、可替换、可测试、可取消的执行链路。

一个最小 Agent 需要完成以下闭环：

1. 接收用户输入；
2. 调用模型；
3. 识别模型返回的文本或工具调用请求；
4. 在安全边界内执行工具；
5. 把工具结果交回模型；
6. 在得到最终回答、发生错误、收到取消信号或超过步数限制时结束。

## 2. 决策

第一版实现为：

- 单进程；
- 单 Agent；
- 单 Provider；
- 工具顺序执行；
- Session 保存在内存中；
- 所有外部依赖都可以替换为离线 Fake；
- 所有运行都可取消并受 `maxSteps` 限制。

核心编排逻辑放在 `AgentLoop` 中。模型厂商差异由 `Provider` 隔离，能力由 `Tool` 暴露，副作用发生前由 `Policy` 决策，操作系统级隔离由 `Sandbox` 提供。

## 3. 系统范围

首版系统负责：

- 管理一次 Agent Run 的生命周期；
- 维护模型可理解的消息历史；
- 通过统一接口调用一个模型 Provider；
- 注册、查找和顺序执行 Tool；
- 在工具副作用发生前执行 Policy 检查；
- 约束文件访问只能发生在 Workspace 内；
- 传播同一个根 `AbortSignal`；
- 产出结构化事件、最终结果和结构化错误；
- 通过 `maxSteps` 防止无限循环。

## 4. 非目标

以下内容不实现，属于首版的 out of scope：

- 多 Agent 协作、委派和调度；
- 多 Provider 动态路由、降级和负载均衡；
- 并行工具执行；
- 图形界面、IDE 插件或完整聊天产品；
- 分布式任务队列和远程执行集群；
- 长期记忆、向量数据库和知识库检索；
- 完整容器编排或生产级 Sandbox；
- 自动修改并提交真实代码仓库；
- 未经用户确认执行高风险外部操作。

这些能力只能在核心协议稳定且有独立 ADR 后引入。

## 5. 最小数据流

```text
User Input
  -> Session
  -> AgentLoop
  -> Provider
  -> Model Response
       |-> Final Text -> Final Result
       `-> Tool Call
             -> Tool Registry
             -> Policy
             -> Workspace / Sandbox
             -> Tool Result
             -> Session
             `-> AgentLoop（下一步）
  -> Event Stream
```

每次循环开始前，`AgentLoop` 都先检查取消状态和 `maxSteps`，再决定是否调用 Provider 或 Tool。

## 6. 术语表

### AgentLoop

本地控制循环。它推进运行状态，调用 Provider，分派 Tool，并判断运行应继续、成功结束还是失败。它不负责实现具体模型协议和工具业务逻辑。

### Provider

模型厂商协议的适配边界。它把内部统一请求转换为厂商请求，再把厂商响应转换回内部事件或消息。首版只启用单 Provider。

### Tool

模型可以请求执行的具名能力。每个 Tool 必须声明输入结构，并返回结构化结果。Tool 不得绕过 Policy、Workspace 或 Sandbox 直接执行受控副作用。

### Policy

副作用发生前的策略判断层，结果至少包括 allow、ask 和 deny。Policy 决定某个动作是否被允许，但不提供操作系统级隔离。

### Sandbox

限制进程、命令或文件操作能力的隔离层。Sandbox 用于降低已经获准执行的动作造成越界影响的风险，不能替代 Policy。

### Run

从一次用户输入开始，到最终回答、错误、取消或达到上限为止的一次执行。

### Session

跨多个 Run 保存对话历史和必要状态的容器。Session 历史不等于运行期间的事件日志。

### Workspace

文件能力允许访问的根边界。路径必须规范化并验证仍位于 Workspace 内。

### Event

运行期间已经发生的可观察事实，例如模型调用开始、工具调用请求、策略拒绝、工具完成和运行结束。

### maxSteps

一次 Run 最多允许推进的循环步数。检查必须发生在下一次模型调用或工具执行之前，不能等副作用发生后再判断。

## 7. 不可变约束

1. 核心组件通过构造参数接收依赖，不直接读取隐式全局配置。
2. Provider 和 Tool 必须能被确定性的离线 Fake 替换。
3. 默认测试不得访问真实网络、真实模型或用户目录。
4. 第一版所有工具调用严格顺序执行。
5. 所有文件读写都必须经过 Workspace 边界检查。
6. 所有可能产生副作用的 Tool 都必须先经过 Policy。
7. Policy 与 Sandbox 是两层独立防护，不能互相替代。
8. 同一个根 `AbortSignal` 必须传递给模型请求和长时间工具操作。
9. 循环次数、模型输出、工具输出和事件缓冲都必须有明确上限。
10. 错误必须是结构化数据，调用方不能依赖错误字符串决定控制流。
11. Session 历史与运行 Event 分开建模。
12. 工具已经可能产生副作用后，不得进行无条件自动重试。

## 8. 副作用边界与提交点

副作用是会改变 Agent 进程外部状态，或消耗不可撤销外部资源的操作。

### 模型调用

- 提交点：请求开始写入网络连接时。
- 提交前：检查取消状态、请求大小和运行预算。
- 提交后：只在能够证明请求未被服务端接受时自动重试；否则交由上层决定。

### 文件写入

- 提交点：第一次对目标文件或临时文件执行写操作时。
- 提交前：规范化路径，验证路径位于 Workspace 内，执行 Policy 判断。
- 提交后：记录成功写入的路径和结果；失败时不得假设文件完全未改变。

### Shell 执行

- 提交点：成功创建子进程时。
- 提交前：解析命令意图，执行 Policy 判断，配置 Sandbox、工作目录、环境变量、超时和取消信号。
- 提交后：记录进程标识和输出；取消时终止进程，并将结果标记为 cancelled，而不是普通失败。

### 用户确认

当 Policy 返回 ask 时，动作尚未提交。只有收到与当前动作匹配的明确授权后，才允许进入副作用提交点。deny 必须在任何副作用发生前终止动作。

## 9. 测试策略

每条重要约束都必须有自动化验证：

- 用 Fake Provider 验证 `AgentLoop` 的文本结束和工具往返；
- 用 Fake Tool 验证调用参数、顺序执行和结果回传；
- 用计数器验证 `maxSteps` 在下一次操作前生效；
- 用 `AbortController` 验证取消信号传播；
- 用临时目录验证 Workspace 拒绝路径穿越；
- 用 Policy Fake 验证 allow、ask、deny 均在副作用前发生；
- 用事件断言验证 Event 顺序和终态唯一；
- 用故障注入验证副作用提交后的操作不会被无条件重试；
- 默认测试通过依赖注入保证不访问真实网络。

Step 00 的验收测试只验证本 ADR 是否存在，并明确记录核心术语、非目标、单 Agent、单 Provider 和副作用边界。后续步骤再用实现测试逐条证明这些约束。

## 10. 影响与取舍

该决策使首版功能较少，但控制流更容易观察，故障更容易复现，测试也不依赖外部服务。顺序工具执行会牺牲吞吐量，单 Provider 会牺牲容灾能力，内存 Session 不支持进程重启恢复；这些都是为先建立正确内核而接受的限制。

## 11. 何时允许改变本决策

只有满足以下条件时才允许修改这些决定：

1. 当前阶段对应的测试已经通过；
2. 新需求无法通过现有边界合理实现；
3. 新行为有独立 ADR，说明兼容性、安全风险和迁移方式；
4. 相关协议有版本策略；
5. 新增并行、多 Agent、多 Provider 或远程执行时，事件顺序、取消语义、权限语义和副作用提交点均有自动化测试。

无论未来如何扩展，Workspace 边界、Policy 先于副作用、可取消、资源有上限和离线可测试仍然是内核不变量。
